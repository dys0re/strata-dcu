# CPU 专家结果直接交给 GPU 合并

后续接入与正常测速见[接入记录](../cpu-result-direct-20261025/README.md)。本文保留接入前的定位证据，不代表当前部署状态。

下一项值得接入的交接优化：**让 GPU 的加权合并直接读取 CPU 专家结果，省掉显存临时结果和前置拷贝节点。**
已在本机做独立原型和测量。尚未接入生产引擎，也没有候选的 decode TPS 或完整回答 QA 结果。

## 当前链路和具体改动

当前 CPU 算完本层专家后，发布完成信号。GPU 随后：

1. 等待 CPU 的完成信号。
2. 从映射的主机内存读取 CPU 专家输出，写进显存临时区；GPU 专家对应行写零。
3. 把 GPU 专家的输出加进临时区对应行。
4. 再读取这些临时结果，按原路由权重依次相乘相加，最后加入共享专家结果。

这条链位于 `src/core/verify.cpp` 的 `post`，底层是 `wait_flag_ge`、
`copy_rows_from_mapped`、`moe_hit_add` 和 `native_moe_combine_multi`。

原型把上述步骤合成一个节点：等待完成信号后，按照真实 GPU 工作表，分别从 CPU 映射内存或
GPU 专家输出区读取，再按原顺序加权。保持 FP32 输出、第一项独立乘法、后续项显式 FMA、
以及 GPU 行原来的 `0.0f + hit`。没有 CPU 端提前求和，没有更换量化格式、丢专家或改变路由。

这里还有一个值得区分的事实：当前二进制使用 `STRATA_HIP_GFX906` 兼容构建，
`verify.cpp` 的编译定义没有 `STRATA_USE_HIP`。因此 `fuse_hits_on()` 落入直接返回 false 的分支；
单设 `STRATA_FUSE_HITS=1` 也不会开启它。等待与拷贝融合在这条兼容路径上可以显式选择，当前默认没有开。
不能把 gfx12 HIP 分支的默认值直接当成本机已启用。
证据是 `postflight.json` 保存的真实编译规则、相同摘要的本地/远程源码，以及当前记录命令。

所以独立测量保留三个对照，而不是只比最慢实现：

| 方法 | 执行内容 |
|---|---|
| 0：当前流程 | 独立等待、拷贝 CPU 行、加入 GPU 行、加权合并 |
| 1：已有融合实现 | 等待放入拷贝；多个位置时 GPU 行加入放入合并；仍有显存临时结果 |
| 2：直接合并原型 | 等待、直接读取两边输出、加权合并，一个节点 |

方法 1 直接调用现有底层实现，用于识别新原型相对已有实现还有多少价值；
不表示当前兼容后端已能通过所有相关环境变量选择它。

## 独立原型结果

真实模型输出宽度 2560，每个位置 10 个路由专家；1–5 个位置；GPU 输出比例
0%、30%、60%、90%、100%，专家位置随机打散。使用固定种子的浮点输出和权重。
这里是合成结果行，不是模型专家的实际计算或实际命中分布。
主机内存显式 coherent+mapped，与当前兼容层对映射分配自动添加 coherent 的做法一致。
生产拷贝、等待、GPU 行加入和合并内核原文保存在 `.inc`，其来源摘要在 `source-origins.json`。

每项七轮，三种方法轮换顺序；热重放每轮预热 20 次、计时 150 次，使用 GPU event。
另一个测试每次更新全部活动 CPU 行，再提交一个 graph 并等它完成，30 次/轮；
计时包含提交和等待完成，不包含 CPU 写入载荷的时间。下表为七个每轮中位数的中位数。
所有原始轮次和逐次值均保留，没有显著性或其他设备速度声明。

GPU 输出比例 60% 时，单位微秒：

| 同时验证的位置 | 当前流程，热重放 | 已有融合，热重放 | 直接合并，热重放 | 当前流程，更新载荷后总延迟 | 直接合并，更新载荷后总延迟 |
|---|---:|---:|---:|---:|---:|
| 1 | 23.07 | 16.35 | 11.93 | 41.21 | 34.56 |
| 2 | 23.76 | 17.19 | 12.91 | 42.02 | 37.08 |
| 3 | 23.69 | 16.54 | 11.86 | 42.94 | 38.17 |
| 4 | 24.28 | 17.84 | 12.85 | 45.39 | 40.79 |
| 5 | 30.19 | 30.83 | 20.91 | 47.01 | 42.67 |

三位置、30% GPU 输出时，热重放当前/已有融合/直接合并为 24.21/16.63/14.87 微秒；
更新载荷后总延迟当前/直接合并为 46.70/41.66 微秒。
收益不只出现在 60% 这一项。完整矩阵见 `analysis.json`。
已有融合在单次提交并等待完成的测试里也会退步，例如三位置、60% 时为 48.03 微秒；
不能只凭热重放结果宣称打开现有融合就会提高应用速度。
0% GPU 输出时新原型相对已有融合也并非总更快，完整记录没有删除这些结果。
100% 仅用于数值覆盖；真实引擎可能跳过整个 CPU 结果通路，不用这组数字估算应用收益。

原测试计数 975 组初始/延迟生产者数值检查，另有 525 次计时后检查；
补充载荷更新测试又做 525 次检查。均相对独立 CPU 顺序 FMA 参考逐位通过，退出码 0。
延迟生产者在 GPU 已提交后等待 50–250 微秒，改变载荷并发布递增完成编号，覆盖两边握手。
这是该形状和种子下的正确性证据，不代替真实模型 QA 或跨设备兼容性。

## 后续接入范围与验收

1. 在 `native_moe.cu` 添加可关闭的直接合并实现；为当前 gfx936 兼容构建显式分发，
   首先只覆盖本机单 GPU、原生 CPU 专家、K=10、1–5 个位置。其他路径沿用原实现。
2. `verify.cpp` 的 `post` 在共享专家侧流已完成后调用它，跳过对应的等待、临时行拷贝和 GPU 行加入。
   继续保留原来的 CPU 输出完成信号和第一层 PLE 完成条件。
   读取结束前不能复用主机输出区；GPU 下一层路由仍在本层合并之后，不能越过这条依赖。
   多 GPU、远端专家、特殊共享 gate、已有全常驻 bypass 等路径分别检查或回退。
3. 接入后跑真实答案、格式、代码执行、STOP/恢复，以及有 miss/无 miss、一个位置和多个位置。
   再在正常、不带全层标记的运行中交替测当前/新实现，固定专家数、模型、增强 MTP 和半显存限制。
   同时观察 CPU 专家等待、结果交接耗时与实际 decode TPS。

当前证据足以选择这个具体优化方向，尚不足以更改默认值或承诺端到端提速。
