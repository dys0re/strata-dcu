## 正常decode：小幅、混合收益

四次冷启动顺序为旧版、新版、新版、旧版。每次先预热128tokens，
再英文/中文/代码各三次256-token生成，最后完整18项语义/格式/代码执行QA及STOP/恢复。
四次退出码均0，全部QA通过。没有开启逐层记录，也没有改变融合选择。
以DONE的decode_ms计算TPS，排除载入与prefill。

固定增强MTP adaptive、宽度上限5、HC Q8、Q8非专家投影/输出头、蒸馏MTP、INT8 KV、512上下文、
12workers加主线程，8500 GPU专家、16076 RAM专家。PLE仍从持久盘读取。
专家交换、PCIe专家分流、lookup和草稿筛选关闭。
全部GPU模型权重29373360352B（42.7543%），上限34351349760B，四次完全相同。
没有把Q8节约的显存用来增加专家。

启动选核不是独占保证，Linux仍可自动迁移内存页；这里只报告实际快照和排队计数。
空闲选核仍为外部测速工具，生产入口的原有CPU绑定策略没有在本轮改变。

## 为什么没有获得原型的10.5%端到端提升

原型的10.5%只覆盖单位置的三次矩阵计算，不含中间量化、线程池、GPU或其他阶段。
正式测试中，CPU专家池每窗口耗时中位数，英文约19.98→19.23ms，代码约27.56→26.70ms。
这些任务的候选位置数相近，但并非固定重放同一批专家，不能作为纯算子速度比。
剩余执行流程没有被这次改动加速，因此整体收益更小。

中文还出现了候选长度变化：旧版每轮平均位置数为3.14–3.80，新版为2.26–3.81，
部分新版请求每轮验证更少、需要更多轮。CPU单轮时间下降不能直接推出TPS上升。
自适应MTP原本就依据实测时间和接受情况选择长度；本轮没有修改该控制器，
也没有单独证明上述长度变化由哪一个因素引起。
不以关闭增强MTP、固定更有利的候选长度或调整专家数来替代这组实际结果。
