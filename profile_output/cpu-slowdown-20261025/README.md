# 骤降到约 9 TPS 的原因：固定核心上的宿主争用

2026-10-25，当前二进制与权重未修改。主要原因已经由两轮同进程换核、再换回的对照确认：
引擎固定使用 CPU0 作为主线程、CPU1–12 作为专家工作线程，这些核心此时有容器外的用户态工作争用。
线程虽已准备运行，却排队等待 CPU。换到 CPU16–28 后排队基本消失，速度恢复；移回又减速。

本次没有修改生产启动默认值、专家数、线程数、量化权重或引擎。不是一次新优化收益测试。
原始文件就在本目录。旧报告所写的“后段减速原因未定位”由本记录补充。

## 为什么能判断存在容器外争用

容器CPU配额是`1500000 100000`，即总CPU时间上限15核；允许CPU掩码是0–127。
这不表示CPU0–12为本容器独占。SMT关闭，本次用的CPU编号对应独立物理核心。

第二轮初始慢速阶段，整个node0的**用户态**CPU消耗相当于13.15核，而整个容器所有CPU上的
用户态消耗合计只有10.94核。即使把容器全部用户态时间都算到node0，那里仍至少有约2.21核
用户态工作来自容器外。node0中断只占约0.03核量级。移回时同样存在差额：12.76对11.18核。
换到node1运行时，node0仍有约3.05核用户态占用。

同时，线程`/proc/PID/task/TID/schedstat`直接显示其可运行但排队的时间。
换核后主线程和专家线程的排队几乎全部消失，移回后恢复，且各段都没有cgroup限流。
这将原因缩小到固定CPU核心上的宿主用户态争用，而不是仅凭全机平均负载或CPU利用率猜测。
当前PID命名空间只显示本容器进程，无法从这里给出竞争者在宿主机的PID或归属。

这些CPU消耗由`/proc/stat`和cgroup计数在同一段decode内取差，按系统SC_CLK_TCK换算。
每200ms采样一次，不读取进程命令行或平台启动参数。

## 内存因素与结论范围

没有主动复制/重新绑定权重；在模型完全载入后，才改变现存线程的CPU掩码。
第一轮Linux自动NUMA平衡确实迁移了部分专家页，不能宣称该轮内存分布严格不变。

第二轮的41.39GiB匿名专家区在三个阶段开始时分布完全相同：
N0=9682028页、N1=1169273页，总计10851301页。尤其换核前与换回前的计数相同，
意味着快阶段并未伴随该区在两个节点间的净迁移。其他较小的匿名区有变化，原始numa_maps保留。
CPU16–28在node1，多数专家页仍在node0，速度仍显著恢复；本次没有将收益归给改善内存本地性。

两轮对照足以确认此次骤降的主要原因。它们不是长期稳定性测试，也没有证明所有速度差距均已消除，
更没有把33.24TPS扩展成中文/代码或其他时段的保证。

## 执行链路为什么会放大抢占

默认核心选择按可用物理CPU顺序取，未根据当时宿主负载选择：
`src/kernels/cpu/pool.cpp`的detect_cpu_topology_impl选择首核为主线程，构造函数逐核固定工作线程。

当前每批专家任务前后会调用`wait_parked`，任务完成还要经过`wait_done`。
`run_native_pipeline`虽已能在结果就绪后提前通知GPU，复用批次描述前仍等待所有工作线程回到等待位置。
一个线程被操作系统切走，就可能让其余线程与后续层继续等待。这种每层重复的交接对核心争用敏感。
这是代码确认的放大机制；本轮没有增加内部计时把“做计算”“等待任务完成”“等待线程归位”各自拆开，
不伪造它们的独立占比。应先避开争用核心，再考虑进一步减少迟到线程拖住整批任务的影响。
